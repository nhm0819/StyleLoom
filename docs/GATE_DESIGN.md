# 생성 결과를 시스템이 스스로 판정하게 만드는 설계

## 현재 도달한 지점

`tools/qc.py`가 완성된 영상을 레퍼런스와 **동일한 프로브**(`media.probe_video`)로 다시 측정하고,
`style.json`의 값과 7개 항목을 대조해 항목별 pass/fail과 통과율(`score`)을 `qc_report.json`에
남긴다. 판정 기준이 사람의 인상이 아니라 재측정 가능한 숫자라는 점, 그리고 판정이 생성 경로와
독립적이라는 점(레퍼런스 프레임을 생성에 넣지 않은 이유 중 하나)이 이 구조의 핵심이다.

한계는 명확하다. **판정이 결과에 아무 영향을 주지 않는다.** `qc.passed`가 False여도 런은
`RunStatus.DONE`으로 끝나고 `final.mp4`는 그대로 남는다. 즉 지금 있는 것은 *리포트*이고
*게이트*가 아니다.

## 시간이 더 있었다면: 실패의 종류를 먼저 분리했을 것

순진한 설계는 "QC 실패 → 전체 재생성 → 재판정" 루프다. 이건 돈을 태우고도 대부분 수렴하지
않는다. 7개 체크 중 재생성으로 고칠 수 있는 것이 절반도 안 되기 때문이다.

| QC 체크 | 실패 원인 | 올바른 대응 |
|---|---|---|
| `saturation` / `contrast` / `warmth` | 생성 모델이 프롬프트의 그레이드를 못 따라감 | **후처리 색 보정** (결정적, 무료) |
| `cut_timing_drift` (per_shot) | trim 실패 | 코드 버그 — 재생성 무의미 |
| `cut_timing_drift` (multi_shot) | 모델이 요청한 타임라인을 무시 | 재생성은 확률적 도박 |
| `avg_shot_sec` / `total_duration` | storyboard 계산 또는 목표 길이 설정 문제 | storyboard 재계산 — 재생성 무의미 |
| `hook_window_shots` | storyboard 버그 | 코드 버그 — 재생성 무의미 |

여기서 나오는 결론이 설계의 뼈대다. **재생성은 최후의 수단이고, 색 편차는 애초에 재생성으로
고칠 문제가 아니다.** `look` 3개 체크는 ffmpeg `eq` 필터로 목표값을 향해 결정적으로 밀 수 있다.
실제 편집자가 하는 일이 바로 그것이고, API 호출이 0회이며, 수렴이 보장된다. 반대로 페이싱 계열
실패는 생성 모델의 잘못이 아니라 **우리 코드의 신호**이므로, 자동 복구가 아니라 시끄러운 실패가
정답이다.

## 4계층 게이트

```
render → assemble → measure ─┬─ 통과            → CERTIFIED
                             ├─ look 편차       → post-grade → 재측정 (최대 2패스)
                             ├─ 샷 단위 파손    → 해당 샷만 재생성 (최대 1패스)
                             └─ 페이싱 불일치   → REJECTED + 원인 보고 (자동 복구 금지)
```

**1계층 — 판정 (구현됨).** 현재의 `qc.py`. 체크를 `blocking`과 `advisory`로 나누는 것만
추가하면 된다. 지금은 7개가 균등 가중이라 `total_duration` 하나가 어긋나도 점수가 0.857로
임계값 0.7을 넘어 통과한다. 통과/실패가 의미를 가지려면 어떤 체크가 결격 사유인지 명시돼야 한다.

**2계층 — 후처리 보정.** `look` 편차를 `eq=saturation=…:contrast=…` 파라미터로 환산하는 순수
함수 하나(`gate.grade_correction(target, actual) -> dict`)와, 그것을 `final.mp4`에 적용하고
다시 프로브하는 루프. 목표값과 실측값의 비율에서 필터 계수가 바로 나오므로 2패스면 수렴한다.
비용 0원, 결정적, 테스트 가능. **투자 대비 효과가 가장 큰 지점이고, 시간이 있었다면 여기부터
했을 것이다.**

**3계층 — 표적 재생성.** 후처리로 못 고치는 실패, 즉 프레임이 검거나 인물이 없거나 클립 길이가
어긋난 개별 샷만 다시 만든다. 여기서 구조적으로 걸리는 지점이 하나 있다. `planner/plan.py`의
`Plan.validate()`는 같은 툴이 플랜에 두 번 등장하면 `PlanError`를 낸다 — 재실행 가능성을 위해
일부러 정적 DAG으로 잡은 결과다. 따라서 retry는 플랜 안에 표현할 수 없다.

다행히 `executor.execute()`가 이미 `plan.validate(frozenset(session.artifacts))`로 **세션이
실제로 들고 있는 아티팩트에 대해** 검증한다. 그래서 수리 패스는 새 개념 없이 표현된다:

```python
REPAIR_STEPS = ("render", "assemble", "qc")   # style/brief/casting/outline/hook/storyboard 재사용
session.put("repair", RepairPlan(shot_indices=[3, 7], pass_number=1))
execute(ctx, session, Plan("repair", REPAIR_STEPS))
```

기존 세션을 그대로 재진입하므로 후크·캐스팅·스토리보드가 보존되고 — 재생성이 다른 영상을 만들어
버리지 않는다 — 지목된 샷만 새로 렌더된다. `render`는 `repair` 아티팩트가 있으면 나머지 샷의
기존 클립 경로를 재사용한다. 상한은 설정값(`gate_max_repair_shots`, `gate_max_passes=1`)으로
고정하고, 모든 시도를 `qc_report.json`에 패스 번호와 함께 누적 기록한다. 자동 재시도가 비용을
말없이 두 배로 만드는 것이 이 종류 루프의 가장 흔한 실패이므로, 상한과 기록은 선택이 아니다.

**4계층 — 인증 거부.** 어느 계층으로도 해결되지 않으면 `RunStatus.REJECTED`(현재 enum에 없음)로
끝내고, `styleloom batch`가 요약에서 이를 구분해 표시한다. 파일은 삭제하지 않는다 — 사람이
확인할 수 있어야 하고, 시스템의 역할은 삭제가 아니라 **인증하지 않는 것**이다. 이 계층만 따로
떼면 30줄 미만이고 API 비용이 0원이므로, 예산이 전혀 없어도 리포트를 게이트로 승격시킬 수 있다.

## 남아 있는 약점: tolerance의 근거가 없다

현재 임계값은 "사람이 차이를 못 느끼는 지점"이라는 추정으로 손으로
정한 상수다. 레퍼런스가 1~2편이라 분산을 알 수 없어서 그 이상 하기 어려웠다. 옳은 방법은
`analyze` 단계에서 레퍼런스 샷별 통계의 **표준편차까지 `style.json`에 저장**하고, tolerance를
그 분산에서 유도하는 것이다. 그러면 "레퍼런스 자체가 흔들리는 폭 안에 있는가"라는, 근거가 있는
질문으로 바뀐다.

출력 길이는 `style.total_duration`을 그대로 따른다(`outline.py`). 이것은 제약이 아니라
목표다 -- 총 길이도 복제 대상인 스타일 속성이므로, 레퍼런스가 10.7초면 출력도 10.7초인 것이
맞다. 다만 나중에 목표 길이를 런 입력으로 받게 된다면 `qc`의 `total_duration` 체크 target이
같은 값을 따라가야 한다. 그러지 않으면 요청을 충족시키는 행위가 곧 QC 실패가 된다. 판정
기준이 스타일에서 오는 것과 런 설정에서 오는 것으로 나뉜다는 뜻이고, `QCCheck`에 기준의
출처(`source`) 필드를 두는 것이 그때의 해법이다.
