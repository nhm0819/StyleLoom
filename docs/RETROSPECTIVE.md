## 출발한 가정

**가정 1 — 스타일은 "느낌"이 아니라 숫자다.**
컷 길이, 총 길이, 채도·명암·색온도, 훅 구간의 컷 수는 픽셀에서 측정 가능합니다.
LLM에게 "이 영상 스타일 설명해줘"라고 물으면 "빠른 컷, 생동감 있는 색감" 같은 답이
오는데, 이건 재현도 검증도 안 됩니다. `avg_shot_sec=1.208`은 둘 다 됩니다.
→ 유지됐습니다. 측정은 OpenCV, 이름 붙이기(그레이드 명칭·카메라 어휘·톤)만 LLM에
넘기는 분업이 그대로 남았습니다.

**가정 2 — 훅의 비결정성은 temperature로는 안 된다.**
temperature만 올리면 같은 아키타입 안에서 표현만 바뀝니다. "아직도 이렇게 하세요?" →
"여전히 이렇게 하시나요?" 는 다른 훅이 아닙니다.
→ 유지됐습니다. 아키타입 추출 / 후보 N개 / top-k softmax 선택, 세 지점을 독립적으로
랜덤화했습니다. 측정값: 8회 반복에서 아키타입 4~6종, 텍스트 8/8 서로 다름.

**가정 3 — 훅은 본문보다 먼저 만들면 안 된다.**
훅은 본문이 지켜야 할 약속입니다. 먼저 만들면 맥락과 무관한 어그로가 됩니다.
→ 유지됐습니다. plan에서 `outline → hook` 순서를 강제하고, `outline.payoff`를 훅
프롬프트에 명시적으로 넣고 "본편이 지키지 못할 것을 미끼로 쓰지 말라"를 시스템
프롬프트에 박았습니다. 순서가 뒤집히면 plan 검증에서 실행 전에 실패합니다.

**가정 4 — 컷 타이밍은 모델에게 맡기면 안 된다.**
→ 유지됐고, 대가가 컸습니다. 아래 "가장 크게 막힌 지점" 참조.

## 어디서 막혔는가

**1. i2v 엔드포인트의 최소 길이 (가장 큰 벽)**

숏폼 컷은 1~2초인데 모든 image-to-video 엔드포인트에 하한이 있습니다. Seedance 4초,
Kling 3초. 화해가 불가능한 충돌입니다. 선택지는 둘이었습니다.

- 샷을 4초로 늘려 하한에 맞춘다 → 페이싱이 죽습니다. 페이싱은 숏폼 스타일의 가장
  핵심적인 속성이고, `style.json`이 존재하는 이유입니다. 1.2초 컷을 못 만드는 시스템은
  레퍼런스를 재현하는 게 아닙니다.
- 하한으로 생성하고 잘라 쓴다 → 돈이 버려집니다.

후자를 택했습니다. 11샷 영상이 Seedance fast에서 11 × 4초 ≈ **$10.64**, 실사용
footage는 **약 9초**. 약 80%를 버립니다. 요구사항에 돈을 쓰고 요구사항을 포기해서
돈을 아끼지 않는 쪽을 골랐다는 게 정확한 표현입니다.

해법은 이후 구현했습니다 (`render_mode=multi_shot`). Kling v3 Pro의 `multi_prompt`는
샷별 길이를 가진 리스트를 한 번의 생성으로 받으므로 하한이 요청 전체에만 걸립니다.
20컷 30초 기준 $6.72 → $3.36, 폐기율 50% → 0%.

**다만 기본값으로 두지 않았습니다.** 컷이 파일 경계에서 모델 출력 안으로 이동하므로,
요청한 타임라인을 엔드포인트가 지켰는지가 보장이 아니라 측정 대상이 됩니다. QC에
`cut_timing_drift`(요청한 각 컷에서 실제 검출된 가장 가까운 컷까지의 평균 거리)를
추가해 이걸 보고하게 했습니다. 오프라인에서는 시퀀스 렌더러가 ffmpeg이라 drift가 항상
0이므로 **배관만 검증됐고 모델의 순응도는 검증되지 않았습니다.** 유료 키로 15초 창
하나($1.68)를 돌려 drift를 읽는 것이 이 모드를 신뢰할지 결정하는 실험입니다.

구현하면서 실제 버그 하나가 드러났습니다. 카메라 무브가 `motion_prompt`에만 들어가고
`image_prompt`에는 없어서, 한 비트 안의 연속 컷들이 **바이트 단위로 동일한 이미지
프롬프트**를 요청하고 있었습니다. 즉 "훅 3초에 컷 2개"가 같은 프레임 두 번이었고,
컷이 보이지 않으니 drift 검사도 이를 감지하지 못했습니다. drift가 7.5초로 나온 것이
단서였습니다.

**2. 엔드포인트 스키마가 조용히 다르다**

fal은 여러 모델을 하나의 queue API로 묶어주지만 하나의 스키마로 묶어주지는 않습니다.

| | Seedance 2.0 | Kling v3 Pro |
|---|---|---|
| 시작 이미지 | `image_url` | `start_image_url` |
| duration | 문자열, 4~15초 | 문자열, 3~15초 |
| 화면비 | `aspect_ratio` 파라미터 | 시작 이미지에서 추론, 파라미터 무시 |
| 인물 참조 | 미지원 | `elements` 배열 |
| 동시 실행 | 미문서화 | 사용자당 1 |

하드코딩된 payload 하나는 자기가 작성된 모델 외 전부에서 실패하고, **파라미터 이름을
무시당하는 방식으로 조용히** 실패합니다. `configs/fal_models.yaml`로 데이터화하고,
payload 생성을 네트워크 호출에서 분리해 키 없이 shape을 테스트합니다. 프로젝트에서
설정 가능성을 의도적으로 사는 유일한 지점입니다 — 대안이 더 단순한 코드가 아니라
틀린 값을 조용히 보내는 코드이기 때문입니다.

**3. 채점자 실행 경로 (점검 중 발견)**

키를 `STYLELOOM_ANTHROPIC_API_KEY`로만 읽고 provider 기본값이 `mock`이었습니다.
채점자가 관례적인 `ANTHROPIC_API_KEY`를 주입하면 빈 문자열을 읽고, provider도 mock에
머물러 **그라디언트 placeholder 영상이 나옵니다.** 예외도 안 납니다. 시스템이 동작하지
않는 것처럼 보이는 최악의 실패 모드였습니다.

`AliasChoices`로 관례적 이름을 함께 받고, provider 기본값을 `auto`(키가 있으면 실제
provider, 없으면 mock)로 바꿨습니다. `doctor`가 무엇으로 해석됐는지 출력하고, 모든
실행이 시작 전에 `providers: llm=anthropic (auto) video=fal (auto)`를 찍습니다.

부수 효과로 회귀가 하나 생겼습니다. pydantic에서 `validation_alias`를 붙이면 필드명으로
값을 넘길 수 없게 되어 `Settings(fal_key="x")`가 예외 없이 `""`가 됩니다. fal 테스트
10개가 이걸 잡았습니다. `populate_by_name=True`로 고치고 회귀 테스트를 남겼습니다.

**4. 모델이 시간 예산을 무시한다**

"비트당 4.2초"를 프롬프트에 넣어도 지키지 않습니다. 7초 레퍼런스에서 19초 영상이
나왔습니다. 프롬프트에서 빼고 `fit_to_budget`으로 후처리했습니다 — 비율은 모델 의도를
따르고, 합계는 코드가 강제합니다. 프롬프트로 협상 가능한 것과 불가능한 것의 경계가
여기였습니다.

## 어떤 모델로 실험했고 무엇을 얻었는가

**정직하게 적어야 하는 부분입니다.** 이 저장소에서 실제로 end-to-end 검증한 것은
오프라인 provider 경로입니다. 유료 API 키가 없어 Seedance와 Kling의 **출력 품질을
나란히 비교하지 못했습니다.** 아래는 실측과 문서 기반 판단을 구분한 것입니다.

**실측한 것 (137 테스트, 네트워크 없음)**
- 스타일 추출이 픽스처의 페이싱을 복원: `avg_shot_sec` 1.2초 ±0.3
- 훅 비결정성: 24회 반복에서 텍스트·아키타입 모두 1종 초과
- recency penalty의 실제 효과: 4,000회 추출에서 해당 아키타입 17.1% → 6.7%
- penalty=0이 사실상 완전 배제로 동작 (20,000회에서 1회)
- 배치 3편의 QC 통과 항목: 페이싱·총길이·훅 윈도우 샷 수
- fal payload shape: 엔드포인트별 파라미터 이름·duration 하한·동시성 상한

**문서 기반으로 선택했고 품질 검증은 못 한 것**
- t2i에 Flux 2 Flex: `image_size` 객체로 9:16을 직접 지정할 수 있어 후처리 크롭이
  불필요합니다. 실제 이미지 품질 비교는 안 했습니다.
- i2v 기본값에 Seedance 2.0 fast: 동시성 제한이 문서화돼 있지 않아 병렬 렌더가 가능하고
  Kling 대비 저렴합니다. 다만 인물 참조를 지원하지 않습니다.
- 크리에이터 일관성이 중요하면 Kling v3: `elements`로 인물 참조를 받는 유일한 경로입니다.
  대신 동시성 1이라 11샷이 순차 실행됩니다.
- LLM에 Claude Sonnet: 비전 지원(레퍼런스 키프레임을 측정값과 함께 전달)과 스키마
  지시 하에서의 JSON 안정성. 그래도 `extract_json`이 코드펜스와 잡담을 방어합니다.

**추론이 아니라 측정으로 답해야 하는 질문들** — 실제 키로 돌리면 바로 나옵니다:
Seedance와 Kling 중 어느 쪽이 이 레퍼런스의 그레이드를 더 잘 유지하는가, 인물 참조가
실제로 6컷을 넘어 동일 인물을 유지하는가, QC 색상 항목이 실제 렌더에서 통과하는가.
현재 QC는 mock에서 0.5~0.8을 냅니다 — 오프라인 렌더러가 색을 맞추려는 시도를 아예
하지 않으므로 그레이드 항목이 **정당하게** 실패합니다. mock이 자기 QC를 통과하게
만들면 QC가 무의미해집니다.

## 시간이 더 있었다면

우선순위 순입니다.

1. **샷 배칭으로 비용 구조를 바꾼다.** 위 "막힌 지점 1"의 해법. 80% 폐기율이 이
   시스템의 가장 큰 결함이고, 다른 어떤 개선보다 효과가 큽니다.
2. **샷 사이즈 분포를 실제로 측정한다.** 현재 페이싱·그레이드는 픽셀에서 뽑지만 샷
   사이즈는 스키마 기본값입니다. 피사체 검출(얼굴 바운딩 박스 대 프레임 비율)이면
   ECU/CU/MS/WS를 분류할 수 있습니다. 레퍼런스가 인물 중심 광고라 이 항목의 부재가
   실제로 결과에 보입니다.
3. **자막 타이밍을 비트에 붙인다.** 현재 자막은 샷 경계에 붙습니다. `pacing.cut_times`와
   추정 BPM이 이미 측정되어 있으므로 `assemble`에 연결만 하면 됩니다. 구현 전까지는
   스키마에 플래그를 두지 않았습니다 -- 값이 있는데 아무 효과가 없는 필드가 실제로
   혼란을 만들었습니다.
4. **오디오.** 지금은 BGM을 사용자가 넣습니다. 레퍼런스의 BPM을 측정하는데 그걸로
   음악을 고르지 않습니다.
5. **훅 A/B 루프.** 이미 후보 N개에 점수를 매기고 있습니다. 선택된 훅과 실제 성과를
   연결할 수 있다면 점수 가중치가 추측이 아니라 학습이 됩니다.

## (가산점) 레퍼런스 기준 충족을 시스템이 스스로 판정하게 하려면

부분적으로 이미 그렇게 되어 있고, 나머지 설계를 적습니다.

**현재 있는 것 — 측정 가능한 항목의 자동 판정**

`qc` 도구가 완성된 영상에 레퍼런스와 **똑같은 probe**를 다시 돌려 숫자를 비교합니다.
같은 측정 함수를 쓴다는 게 핵심입니다. 별도 검증기를 만들면 검증기 자체가 틀릴 수
있습니다.

| 항목 | 목표 출처 | 허용 오차 |
|---|---|---|
| avg_shot_sec | `style.pacing` | ±0.6초 |
| total_duration | `style.total_duration` | ±6초 |
| saturation / contrast / warmth | `style.look` | ±0.18 / ±0.20 / ±0.12 |
| hook_window_shots | `style.hook_style.cut_count` | ±0.5 |

6개 중 통과 비율이 점수이고 0.7 이상이면 통과입니다. 허용 오차는 "사람이 차이를
못 느끼기 시작하는 지점"에 맞췄고, mock이 통과하도록 맞추지 않았습니다.

**설계상 빠져 있는 것과 어떻게 채울 것인가**

*(a) 분포 비교로 격상.* 지금은 평균 대비 평균입니다. 컷 길이 분포 전체를 비교하는 게
맞습니다 — 평균 1.2초는 "전부 1.2초"와 "0.4초와 2.0초의 교대"를 구분하지 못하고, 후자는
전혀 다른 편집 리듬입니다. `pacing.cut_times`가 이미 저장돼 있으므로 레퍼런스와 출력의
컷 간격 분포에 Wasserstein 거리나 K-S 검정을 쓰면 됩니다. 코드 몇 줄이고, 이게 다음에
할 일입니다.

*(b) 판정 불가 항목에 VLM 심사.* 자막 가독성, 훅 3초의 시선 유지력, 인물 동일성은 숫자로
안 나옵니다. 설계는 이렇습니다 — 레퍼런스 키프레임과 출력 키프레임을 **쌍으로** 제시하고
루브릭 기반 점수를 요구합니다. 절대 평가("이 자막이 읽히나?")가 아니라 상대 평가("어느
쪽이 레퍼런스에 더 가까운가, 어느 축에서 벗어났는가")여야 합니다. 절대 평가는 모델의
사전 취향에 흔들리고, 쌍 비교는 레퍼런스에 고정됩니다. 출력은 자유 서술이 아니라
`{axis, verdict, evidence}` 구조여야 재시도 로직에 연결할 수 있습니다.

*(c) 실패를 재시도로 연결.* 현재 QC는 리포트를 쓰고 끝냅니다. 항목별로 책임 단계가
정해져 있으므로 자동 수정이 가능합니다: 페이싱 실패 → storyboard 재계산, 색상 실패 →
그레이드 토큰 강화 후 해당 샷만 재렌더, 훅 윈도우 실패 → hook_style 위반이므로 즉시
중단. 실패 항목 → 재시도 대상 단계의 매핑은 이미 tool의 `reads`/`writes` 선언에 들어
있습니다. 다만 렌더 비용을 고려하면 재시도 상한을 명시적으로 걸어야 합니다.

*(d) 자기 판정의 함정을 인정.* 시스템이 자기 출력을 채점하면 채점자를 만족시키는
방향으로 수렴합니다. 그래서 **판정 기준은 레퍼런스에서 나오고 시스템이 만지지 못하는
곳에 있어야** 합니다. 지금 `style.json`은 사람이 수정 가능한데, 그건 의도적으로 이
경계를 사람 쪽에 둔 것입니다. 각 실행이 `style_used.json`으로 자기가 쓴 기준을
스냅샷하는 이유도 같습니다 — 기준이 바뀌면 점수 비교가 무의미해지므로, 어떤 기준으로
채점됐는지가 기록에 남아야 합니다.
