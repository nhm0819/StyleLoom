# 회고

## 출발한 가정

1. 프롬프트로 생성한 이미지가 이후 영상 생성 시 특징을 계속 이어지도록 해준다.
2. 샷마다 각각 영상을 생성하는 것보다 multi-prompt로 context를 이어가는 것이 효율적이다.
3. Kling 모델도 충분히 영상 생성 능력이 좋다.

---

## 어디서 막혔는가

**API 세대 불일치가 조용히 성공한다.**
코드는 레거시 `/v1/videos/*` 형태로 쓰여 있는데 타깃은 Kling 3.0이었다. 3.0에서
`model_name`·`mode`·`negative_prompt`는 **모르는 키라서 무시**되고, 요청은 `succeeded`로
돌아오며 기본값 5초가 생성된다. 폴링도 `data.task_id → data.id`, `succeed → succeeded`,
단일 객체 → 배열로 전부 달랐다. 문서를 코드와 한 줄씩 맞춰보기 전까지 드러나지 않았다.

**두 엔드포인트의 글자수 예산이 5배 차이인데, 그걸 모른 채 프롬프트를 짰다.**
샷당 512자(하드 리밋), 이미지 2500자. 측정해 보니 고정 스타일 토큰이 512자 중 **415자**를
먹고 실제 샷 묘사에 40자만 남았으며, 부족분은 `fit()`이 **QC가 채점하는 컬러 그레이드를
조용히 버려서** 메꾸고 있었다. 그리고 레퍼런스 묘사 7개는 이미지 프롬프트에 **0개** 도달했다
— 2500자 예산의 8%만 쓰면서.

**1초 미만 페이싱은 렌더할 수 없다.**
레퍼런스는 0.76초마다 컷하고 엔드포인트의 최소 컷은 1초다. 엔드포인트 격자에 맞춰 계획하는
쪽을 택했고, 그래서 페이싱은 **구조적으로 31% 어긋난다.** QC 허용치를 그 강제 격차만큼만
넓히고, 넓힘이 적용되면 "통과가 재현을 뜻하지 않는다"고 경고한다.

**공통 패턴: 조용히 실패하는 것들.**
ffmpeg는 프레임 밖에 자막을 그려도 에러를 내지 않는다 (폰트 크기를 높이에서 뽑아 9:16에서
양쪽이 잘렸다). `multi_shot`의 기본값은 `true`다. 그리고 **오프라인 프로바이더가 선언하지
않은 제약은 유료 실행 전까지 아무도 검증하지 않는다** — 프롬프트 상한, 요청당 샷 수(14컷이
1요청으로 통과), 정수초 격자에서 같은 실수를 세 번 반복했다.

## 어떤 모델로 실험했고 무엇을 얻었는가

**Kling** 모델로 실험했고, 기본값이 상당히 동양인 외모이면서 또 무난한 감성 위주였다.

**실측한 것**

| 항목 | 이전 | 이후 |
|---|---|---|
| 자막 기하 | 12자 한 줄이 720px 프레임에서 720px로 잘림 | 594px로 수정, 위치·줄간격도 픽셀로 검증 |
| 프롬프트 예산 | 이미지 프롬프트 212자 / 레퍼런스 묘사 0/7 도달 | 561자 / 5개 차원 전부 도달 |
| 윈도우 패킹 산술 | — | 14컷 → 6/6/2 세 요청, duration 6/6/3초, 합계가 `settings.duration`과 일치 |
| 길이 충실도 | 10.7초 영상에 15초 과금 (40% 초과) | 요청 = 과금 = 산출 |
| 훅 비결정성 | — | 반복 실행에서 아키타입·텍스트 모두 1종 초과, recency penalty 실효 확인 |

**문서 기반으로 선택했고 품질은 비교하지 못한 것**

- **Kling 3.0 i2v**를 기본으로 — `contents`의 타입 있는 first_frame과 요청당 샷 리스트가
  레거시·omni에는 없다. 레거시 자격증명은 3.0 이후 모델을 못 쓴다.
- **Kling Image** — 참조 이미지를 받아 같은 인물을 재생성하는 경로라서 골랐다. 이미지
  품질 비교는 안 했다.
- **Claude Sonnet** — 한국어 카피와 vision을 한 모델로 처리하려고. JSON 안정성은 스키마
  지시로 확보했다.

### 모델 다양성을 확보하지 못한 것 — 가장 아쉬운 지점

**한 벤더, 한 모델로만 전체 파이프라인을 검증했다.** Kling을 고른 근거는 "3.0이 문서상
요청당 샷 리스트와 타입 있는 first_frame을 지원한다"는 것뿐이었고, 이건 *기능 지원 여부*를
비교한 것이지 *생성 품질*을 비교한 게 아니다. 다시 말해 이번 시스템이 실제로 검증한 것은
"Kling API를 정확하게 호출하는 하네스를 만들 수 있는가"이지, "Kling이 이 스타일을 재현하기에
가장 좋은 선택인가"가 아니다. 후자는 답한 적이 없다.

이게 왜 문제인지 구체적으로 짚으면:

- **비교 기준이 없다.** Veo 3, Seedance, Runway, Pika 등 동급 상용 API 중 어느 것도 같은
  레퍼런스·같은 프롬프트 예산으로 나란히 돌려보지 않았다. Kling의 결과가 "이 스타일 재현에
  괜찮은 수준"인지 "이 카테고리에서 평균 이하인데 그냥 처음 고른 것"인지 구분할 방법이
  지금은 없다.
- **실패 모드가 Kling 고유의 것인지 일반적인 것인지 모른다.** 예를 들어 컷 타이밍 드리프트나
  인물 정체성 유지 실패가 Kling API의 한계인지, 아니면 multi-shot 방식 자체의 한계인지는
  다른 벤더에서 같은 실험을 반복해봐야 갈린다. 지금은 원인이 하나로 뭉뚱그려져 있다.
- **캐스팅 풀의 "동양인·무난한 감성" 편향도 Kling 기본값에서 관찰된 것**이라, 이게 이
  모델 특유의 편향인지 숏폼 학습 데이터 전반의 편향인지 다른 모델과 비교하지 않고는 알 수 없다.
- 시간·비용 제약상 한 벤더로 좁힌 것 자체는 합리적인 선택이었지만, 그 선택을 "실험해서 나온
  결론"이 아니라 "제약 때문에 못 한 비교"로 명확히 구분해 두지 않으면, 나중에 이 하네스를
  다른 모델로 확장할 때 지금의 프롬프트 예산·윈도우 패킹 로직이 얼마나 Kling 전용 가정에
  의존하고 있는지 다시 처음부터 파악해야 한다.

---

## 시간이 더 있었다면

1. **여러 모델로 같은 실험을 반복한다 (Veo 3, Seedance 등).** 같은 레퍼런스, 같은 프롬프트
   예산, 같은 QC 축으로 Kling과 나란히 돌려서 지금 Kling에서 관찰된 편향·드리프트·품질이
   모델 특유의 것인지 구조 전체의 것인지를 가른다. 이번 회고에서 가장 크게 빠진 검증이다.
2. **캐스팅 조건을 더 느슨하게 하거나, 더 다양한 조건을 걸어 다양한 영상이 생성되도록 한다.**
3. **QC gateway에 대해 더 정확한 조건들을 조사한다.**
4. **1초 미만 페이싱 복구.** 윈도우 클립을 계획된 컷 경계에서 쪼개 각 조각을 요청 길이로
   트림한 뒤 재결합한다. 윈도우당 ffmpeg 1패스, **생성 비용 증가 없음.** 페이싱과 길이를
   동시에 되찾는다.
5. **프롬프트에 대해 더 고민해보았을 것이다.**

## (가산점) 레퍼런스 기준 충족을 시스템이 스스로 판정하게 하려면

**1단계 — 숫자 게이트 (이미 있는 것을 게이트로 바꾸기).**
QC는 이미 페이싱·총길이·색 3축·훅 윈도우 컷 수·컷 드리프트를 스타일 대비로 잰다. 여기에
항목별 **심각도**를 부여한다: 색은 재시도로 고칠 수 있고, 컷 드리프트는 요청 구조를 바꿔야
하고, 길이는 계획을 다시 세워야 한다.

**2단계 — 실패 항목이 재시도 방식을 지정한다.**
재추첨(re-roll)은 안 된다. 무엇이 틀렸는지 알면서 같은 주사위를 다시 굴리는 것이기 때문이다.
대신 실패 항목 → 입력 변경이 1:1로 대응해야 한다. 색 실패 → 이미지 프롬프트의
`palette`·`grade` 강화. 드리프트 실패 → 윈도우당 샷 수 감소. 길이 실패 → 격자 재계획.
각 재시도는 무엇을 왜 바꿨는지 런 폴더에 남긴다.

**3단계 — VLM 심판, 단 숙제를 자기가 채점하지 않게.**
숫자로 볼 수 없는 것(같은 인물인가, 제품이 보이는가, 레퍼런스처럼 보이는가)은 결과물
프레임과 **레퍼런스 프레임을 나란히** 놓고 VLM에 묻는다. 결정적 제약: 심판에게 **스타일
추출에 쓴 그 프레임을 주면 안 된다.** 자기가 만든 라벨을 근거로 자기 출력을 채점하는
순환이 된다. 레퍼런스에서 별도로 홀드아웃 프레임을 떼어 둬야 한다.

**4단계 — 진짜 주장은 자기일관성이다.**
"같은 시스템이 다른 입력을 같은 스타일로 만든다"는 명제는 한 편으로는 증명되지 않는다.
같은 입력을 두 번 돌린 결과가, 다른 입력으로 만든 결과보다 **측정 축에서 서로 더
가까워야** 한다. 이건 사람의 판단 없이 계산 가능하고, 하네스가 스스로 돌릴 수 있는 유일한
"스타일을 지켰는가" 검사다. 지금 없는 것이고, 있다면 위의 게이트 임계값을 스타일마다
자동으로 정하는 근거도 된다.
