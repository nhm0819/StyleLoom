# `run_{n}/` 안의 파일들

한 번의 실행(run)은 스테이지를 순서대로 통과합니다. 각 스테이지는 끝날 때마다
JSON(또는 미디어) 파일 하나를 씁니다 — **다음 스테이지로 넘어가기 전에 반드시
씁니다.** 그래서 런이 중간에 실패해도 어디까지 갔는지, 실패 직전까지 뭘 결정했는지
전부 파일로 남습니다.

스테이지 순서 = 아래 파일이 만들어지는 순서입니다:

```
ingest → casting → outline → hook → storyboard → keyframe → render → assemble → qc
```

---

## 최상위 파일

### `run.json`
런 전체의 상태판. 상태(`running`/`done`/`failed`), 현재/마지막 스테이지, 실패 시
에러 메시지, 이번 런이 실제로 뽑은 훅 문구·아키타입, QC 점수, 그리고 이 런이 실행된
**플랜의 스텝 목록**이 들어 있습니다. 런이 재개(resume) 가능한지, 어디서 멈췄는지는
이 파일 하나만 보면 압니다.

### `inputs.json`
사용자가 **원본 그대로** 넘긴 입력의 스냅샷 — 입력 텍스트, 첨부 파일 경로, BGM
경로, 언어. `brief.json`과 다른 점: 이건 가공 전 원본이고, 브리프는 이걸 정규화한
결과물입니다.

### `style_used.json`
`style.json`(레퍼런스에서 추출한 스타일 자산)을 이 런이 실행된 시점 그대로
**스냅샷**한 것. `style.json`은 런 사이사이 사람이 손으로 고칠 수 있는 재사용
자산이라, 런 폴더에 그 시점의 사본을 박아두지 않으면 나중에 "이 영상은 그때
정확히 어떤 스타일 설정으로 나온 거지?"에 답할 수 없습니다.

### `brief.json`
`inputs.json`을 정규화한 결과 — 주제(topic), 핵심 메시지(key_message), 타겟
청중(audience), 사실 목록(facts), 언어. 텍스트/이미지/비디오 어떤 입력이든 이
하나의 형태로 수렴합니다. `outline`/`hook`/`casting`(특화 단계)이 전부 이걸 읽습니다.

### `casting.json`
이번 런에 뽑힌 **인물(creator)과 배경(setting)**. 각각에 대해:
- `id` — 추첨된 풀(`configs/casting.yaml`) 항목의 id (recency 페널티·히스토리가
  전부 이 id로 연결됩니다)
- `seed_prompt` — 풀에서 뽑힌 원본 설명 (특화 전)
- `prompt` — 브리프에 맞춰 LLM이 다시 쓴 최종 설명 (실제로 모든 샷 프롬프트에
  들어가는 값)
- `creator_pool` / `setting_pool` — 이번에 추첨 대상이었던 전체 풀의 id 목록
  (재현성/감사용)
- `entropy_source` — 난수 출처 (`SystemRandom`, OS 엔트로피)

세 번의 런이 같은 입력이라도 서로 다른 인물·장소를 뽑을 수 있어야 한다는 요구사항이
여기서 증명됩니다.

### `outline.json`
바디 구간의 뼈대 — `beats`(각 구간의 이름·의도·내용·자막·길이)와 `payoff`(훅이
반드시 지켜야 할 약속). 훅보다 먼저 만들어집니다. 훅이 이 payoff를 참조해야
"맥락에 맞는 훅"이 되기 때문입니다.

### `hook.json`
첫 3초 결정의 **전체 감사 기록**: 후보로 쓰인 아키타입 풀, 이번에 추첨된
아키타입, 생성된 모든 후보 문구(점수 포함), 최종 선택된 것, 선택 방식
(top-k softmax), 온도(temperature), 엔트로피 출처. "훅은 시스템이 생성하고,
같은 입력으로 재실행해도 달라질 수 있어야 한다"는 요구사항이 여기서 증명됩니다.

### `storyboard.json`
샷 단위 설계도. `hook_text`/`hook_archetype`(위 결과 반영) + `shots` 배열. 각 샷은
길이, 샷 사이즈(CU/MS/WS 등), 카메라 무브, 액션 설명, 화면 자막, 그리고 실제
비디오 생성 API에 보낼 프롬프트(`scene_prompt`/`motion_prompt`, 이어지는 샷은
`continuation_prompt`)를 담고 있습니다. 512자 캡에 맞춰 다듬어진 최종 텍스트가
여기 있습니다.

### `keyframe.json`
이번 런의 **앵커 이미지 경로**와, 각 렌더 요청(윈도우)의 **첫 프레임**이 어떤
샷을 위해 생성됐는지의 매핑. 이미지 자체는 `keyframes/`에 있고, 이 파일은 "어떤
파일이 어떤 샷용인지"를 기록합니다 — 이미지 픽셀만 봐서는 복원 불가능한 정보라서
따로 남깁니다.

### `render.json`
어떤 클립 파일이 어떤 샷 인덱스들을 담고 있는지, 요청한 길이 vs 실제로 과금된
(엔드포인트가 정수초로 반올림한) 길이, 그리고 실패한 샷이 있다면 그 에러 메시지.
경로만 저장하고 바이트는 저장하지 않아서, 실패한 런도 어디까지 살아남았는지
바로 보입니다.

### `assemble.json`
최종 비디오 파일 경로와 자막이 실제로 몇 개 번인(burn-in)됐는지(`captioned_count`).

### `qc_report.json`
완성된 영상이 원본 스타일에 얼마나 부합하는지 측정한 결과 — 체크 항목별
목표값/실측값/허용오차/통과여부, 종합 점수, 전체 통과 여부.

### `concat.txt`
ffmpeg의 `concat demuxer`가 읽는 임시 목록 파일. `captioned/` 안의 세그먼트들을
어떤 순서로 이어붙일지 나열합니다. 사람이 볼 파일이라기보단 ffmpeg 호출의
부산물이라 크게 신경 쓰지 않으셔도 됩니다.

### `final.mp4`
**완성된 최종 숏폼 영상.** 이게 실제 제출/배포 결과물입니다.

## 하위 폴더

### `keyframes/`
- **`anchor.jpg`** — 런 전체에서 딱 1장. 캐스팅으로 뽑힌 인물·장소·컬러 그레이드로
  생성된 "정체성 기준 사진". 영상에 직접 쓰이지는 않고, 아래 `lead_NN.jpg`들이
  전부 이 이미지를 레퍼런스로 삼아 생성됩니다 — 그래서 컷이 여러 번 나뉘어
  생성되어도 같은 사람·같은 옷·같은 톤이 유지됩니다.
- **`lead_00.jpg`** (`lead_NN.jpg`) — 각 렌더 요청(윈도우)의 **시작 프레임**.
  앵커를 참조 이미지로 써서 생성되며, 그 윈도우의 첫 샷이 요구하는 구도·앵글을
  반영합니다. Image-to-Video 호출 시 첫 프레임으로 들어갑니다. 파일명 번호는
  그 윈도우를 여는 샷의 인덱스입니다.

### `shots/`
- **`win_00.mp4`** (`win_NN.mp4`) — Kling에 보낸 **한 번의 생성 요청**이 돌려준
  원본 클립. 하나의 파일이 샷 1개가 아니라 **여러 컷을 담은 하나의 윈도우**일 수
  있습니다(멀티샷 세미콜론 포맷으로 최대 6컷/15초까지 한 번에 요청). 예시처럼
  파일이 1개뿐이면 이 영상의 전체 스토리보드가 요청 1번(윈도우 1개) 안에 다
  들어갔다는 뜻입니다. 아직 자막이 없는 **원본** 영상입니다.

### `captioned/`
- **`seg_00.mp4`** (`seg_NN.mp4`) — 위 `shots/win_NN.mp4`에 자막을 구워넣은
  버전. 개수와 순서는 `shots/`와 1:1로 대응합니다. 이 세그먼트들이
  `concat.txt` 순서대로 이어붙어 `final.mp4`가 됩니다.

## 한눈에 보는 데이터 흐름

```
inputs.json ──▶ brief.json ──▶ outline.json ──▶ hook.json ──▶ storyboard.json
                     │                                              │
                     └──────────▶ casting.json ◀────────────────────┘
                                       │
                                       ▼
                              keyframe.json + keyframes/(anchor.jpg, lead_NN.jpg)
                                       │
                                       ▼
                              render.json + shots/win_NN.mp4
                                       │
                                       ▼
                         assemble.json + captioned/seg_NN.mp4 + concat.txt
                                       │
                                       ▼
                                  final.mp4
                                       │
                                       ▼
                               qc_report.json
```

`run.json`은 이 전체 흐름의 진행 상황을 실시간으로 기록하는 상태 파일이라
위 그림 어디에도 화살표로 끼워 넣지 않고 별도로 존재합니다.
